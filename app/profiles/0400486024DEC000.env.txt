# The Legend of Zelda: Ocarina of Time (Switch 2, 0400486024DEC000) on an iPhone: a STARTING POINT for the fluidity, NOT measured on a device.
#
# Where it goes: the app's Documents folder, as  games/0400486024DEC000/env.txt  (Files app > On My iPhone > the app > games > 0400486024DEC000). The app reads it at each boot, one NAME=value per line,
# only DM_* and MTL_* names; a switch the settings sheet already sets wins over this file. Remove a line to go back to the registered profile's behaviour.
#
# What the engine's own notes say about this game (dm/games/0400486024DEC000/README.md): on Apple GPUs its cost "hardly depends on the resolution" (mesh, compute and the game's neural upscaler with
# a FIXED 2048x1152 input dominate: 683x384 cost 14.3 ms, 1536x864 14.7 ms), so lowering the resolution is not the lever. The two that can matter on a phone are the upscaler and the frame budget.

# Cap at 30 fps: a 33 ms frame budget instead of 16.7. The game steps its time by a frame ratio, and the profile's frame-step stub makes it follow the host's frame step, so 30 plays at normal speed, not slow motion.
DM_FPS_TARGET=30

# Replace the game's own upscaling network (agl's NDSR, a large fixed GPU cost here) with MetalFX's spatial scaler (docs/env_switches.tsv: DM_UPSCALER). The engine measured MetalFX's present upscaling at no
# measurable GPU time on a Mac; the picture differs from the console's, and a failure shows as a wrong or black upscaled image: if so, delete this line.
DM_UPSCALER=metalfx

# Handheld mode (the iPhone's own use: lower resolution, the handheld controller layout). The engine also switches to it by itself when an iPhone overheats.
DM_OPMODE=0

# Frame rate at the top left: read what the phone really does, then send the log back.
DM_SHOW_FPS=1

# The first Play's "Preparing shaders" step (the host's pipeline prewarm, built BEFORE the first picture). This game's seed list holds 14,748 lines (the engine's dm/games/0400486024DEC000/pso_manifest.tsv) and the first Play
# used to build all of them (the phone reported about 25,000 shaders compiled: far too long). Everything in this block is a COMMENTED example, none of it is active, and none of it is needed. NOT measured on a device: DM_PSO_PREPARE_PERCENT
# and DM_PSO_PREPARE_TAIL are engine switches that arrive with engine patch 0412; a host built without it ignores them.
#
# DM_PSO_PREPARE_PERCENT=<1..100>: how much of the prewarm lists (this game's seed list, then this device's own games/0400486024DEC000/pso_user.tsv) is built before the first frame; the rest is built by a background pass while you play (a pipeline
# still missing when a draw needs it is built on the spot: for this game, whose seed list is longer than 10,000 lines, the app leaves DM_PSO_NOWAIT to the host's 1, so that draw waits at most
# 50 ms a frame and is skipped until it is built; a game with a shorter list waits for it, DM_PSO_NOWAIT=0). 100 = all of it first, as before. The app now sets BY ITSELF the share that makes about 500 lines (2% of the 25,163 lines of the pack built on the phone,
# 4% of the engine's 14,748): you do not need a line for that. (It used to set 50: 13,066 lines, 1,061-1,708 s at every Play on an iPhone 15 Pro, 2026-11-20.) To get the old behaviour back (everything before the first frame, a long first Play), uncomment this line:
# DM_PSO_PREPARE_PERCENT=100
# or to try another share (a smaller one starts sooner and leaves more to build while you play):
# DM_PSO_PREPARE_PERCENT=25
#
# DM_PSO_PREPARE_TAIL=0: do not run the background pass at all, so what is not in the first share is built only when a draw needs it (a hitch while playing, instead of work in the background). Default (no line): the pass runs.
# Only useful with a PERCENT below 100.
# DM_PSO_PREPARE_TAIL=0
#
# DM_PSO_PREPARE_THREADS=<n>: how many workers build the pipelines. The engine's default is the number of active cores. A TEST line to try more workers than cores (the compiles overlap more); each worker holds a shader compiler's memory,
# so a high number risks the iPhone's memory ceiling and the app being killed during "Preparing shaders": lower it again if that happens.
# DM_PSO_PREPARE_THREADS=8

# The settings sheet's "Profile" row (2026-11-20): this game starts at "Memory saver" = handheld, dynamic resolution, 30 fps, render scale 0.5, DM_PSO_PREBUILD=0 and DM_PSO_PREPARE_TAIL=0
# (the Apple TV port's memory set). A line here wins over the profile for that switch; "Standard" in the sheet turns the profile off.

# ---- Engine patches 0413-0415 (2026-11-21): what the host does by itself, and the switches to turn it back. NOT measured on a device; read the device log after a session.
# After the device session of 2026-11-20 (44 min, 9,022 frames): 930 s of frames went to compiles the draws waited for (350 s shader libraries, 580 s pipelines: 196 s for 136 compute
# pipelines, 92 s for 57 mesh pipelines), the learned list stayed at 2 lines, and the pipeline cache wrote nothing in the first session and dropped 451 of 472 pipelines in the second.
# With those patches, by default (no line needed):
#   * games/0400486024DEC000/pso_user.tsv records every row the game asks for on this phone (also the ones the pack's list holds), crash-safe, and the prewarm builds it FIRST: the
#     ~500 lines before the first frame and the background pass are then what this phone drew in earlier sessions. Back to the old list and order:
# DM_PSO_USER_FIRST=0
#   * the pipeline cache (games/0400486024DEC000/pipelines-<chain>-<gpu>.mtlarchive) keeps render, compute AND mesh pipelines, holds additions back while the phone is hot instead of
#     dropping them, is written at every background / quit / end, and survives a failed write. "Pipeline cache" off in the settings (or this line) turns it off:
# DM_PSO_BINARY_ARCHIVE=0
#     Its caps (engine 0414 revision 2): 24 MB and 400 pipelines by default. Do NOT raise them before the open has been measured on the phone: opening the archive costs memory that
#     grows with the SQUARE of its size and is not given back (on a Mac: 23 MB / 400 pipelines +46 MB, 69 MB / 1,200 +367 MB, 103 MB / 1,800 +843 MB), and this game already ends
#     sessions near 4.2 GB. The log line "pipeline binary archive: opened ... available memory X MB before, Y MB after" is that measurement. A guard turns the archive off and deletes
#     the file when an open costs more than DM_PSO_ARCHIVE_GUARD_MB (150). Only after a measured A/B, for example:
# DM_PSO_ARCHIVE_COUNT=800
# DM_PSO_ARCHIVE_MB=48
#   * the background pass goes on from where the last session left the pack's list (games/0400486024DEC000/pso_tail.tsv) instead of starting it again, and its rows from the pack's
#     list wait while the phone is hot (thermal state serious or critical); this phone's own rows go on. Back to the 0412 behaviour (walk everything again, compile while hot):
# DM_PSO_TAIL_RESUME=0
# DM_PSO_TAIL_HOT=1
#   * the Memory saver profile turns the background pass off (DM_PSO_PREPARE_TAIL=0). A middle way, to try in an A/B on the phone (memory peak, the "[longframe]" waits): the pass
#     builds only what this phone drew before, nothing from the pack's list:
# DM_PSO_PREPARE_TAIL=user

# ---- Switches that only a device run can judge (an A/B plan, none of them active; same scene, same thermal start, 10 minutes each, then send the log):
#   * DM_PSO_NOWAIT: for this game (25,163 seed lines, more than 10,000) the app leaves the host's own 1: a draw waits at most DM_PSO_NOWAIT_MS (50 ms a frame, all draws together),
#     then is skipped until the background build is done: no frozen frame, but objects may be missing for a moment. With 0 a draw waits for its pipeline or library: the 161 s and
#     118 s frames of the 2026-11-20 log. The game's settings sheet ("Skip draws while they compile") shows ON for this game and can turn it off; or, here:
#     A/B: the "[longframe]" lines and frame p95 vs. what the screen shows while a new area loads.
# DM_PSO_NOWAIT=0
#   * DM_QOS_MAP=1 would change almost nothing here: 99 % of the guest CPU (4,009 of 4,039 ms/s, "threads up to frame 8700") is at Switch priority 44, which the map's default edges
#     (44,59) keep user-interactive. Moving the game's workers (priority 44) needs DM_QOS_EDGES=43,59 as well, which may starve them: only as an A/B with the "power" and "timing" lines.
#   * DM_RT_SHARE (default 0.4,0.55 on iOS): the acquire thread declares 13.33 ms of each 33.33 ms period and used 23.7 ms a frame at 1.61 GHz; a larger share (e.g. 0.6,0.6) is an A/B
#     for the "thread policy" line's "demoted in N of 300 frames" and the frame p95, not a fix.
#   * DM_FPS_TARGET=60 is NOT advisable for this game on this phone: the GPU took p50 19-25 ms a frame in 3D play at render scale 0.5 (the "timing" lines), over the 16.7 ms budget, and
#     the engine holds 30 fps anyway while the phone is at thermal state 2 or more.

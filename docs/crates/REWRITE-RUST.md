# REWRITE-RUST: the Switch NSO rewriter in Rust

Crates: `ibuilder-nso` (loader), `ibuilder-a64` (encoders + Capstone decoder), `ibuilder-rewrite` (the rewriter, library +
`ibuilder-rewrite` CLI). Port of `engine/dm/tools/patch_nso.py` and the modules it imports. Goal order: byte-identical
output, then speed, then memory, no embedded runtime. Progress journal: the appendix at the end of this file.

**Status: all three Grizzy modules (sdk, subsdk0, main) are byte-identical to the Python oracle on every output file and
on the printed log; the iOS device and simulator targets build; the simulator binary reproduces the same bytes.**

Python's `re` patterns over Capstone's operand text in the tail-call recognisers are kept verbatim through the `regex` crate
(ASCII mode; each worker thread compiles a pattern once, `ins::full`); the hot scans use word-level tests instead.

## Run

```
ibuilder-rewrite [--threads N] [--game ID] [--games-dir DIR] [--py-tools DIR] [--spin-list] <module file> <out dir> <name>
```
Env compatibility: `DM_REWRITE_J`, `DM_GAME`, `DM_GAMES_DIR`, `DM_SPIN_LIST`. The lines the Python prints go to stdout. The
Python's `os.execve` re-run (patch area too big for the gap before the base) is the loop in `rewrite()`; the library API is
`ibuilder_rewrite::rewrite(&file, name, name, &Options)`. `IBR_TIMING=1` prints per-phase times to stderr. `ibuilder-rewrite --list-ported` prints what this build can rewrite per game (the coverage rows; `scripts/check-patch-coverage.sh` compares them with the engine's).
`--py-tools <engine dm/tools>` additionally writes `build_src.sha256`: the oracle's file hashes the Python sources of the
copy it ran from (`out-py/pyrewrite/dm/tools`, the iOS-patched one: its `patch_nso.py` differs from the engine's), so it only
matches with that folder.

## Performance (release, `/usr/bin/time -l`, shared 8-core M1 Pro; the machine was loaded by other agents: indicative only)

(The first measurements of the port; the current numbers are in "Update (R5)" below.)

| module | Rust 1 thread | Rust 8 threads | Python serial (CONVENTIONS) | Python fork pool |
| --- | --- | --- | --- | --- |
| main | 9.2 s, 490 MB max RSS, 350 MB footprint | 4.2 s, 430 MB, 335 MB | 200.5 s, 4.13 GB, 12.5 GB | 69.6 s, 1.94 GB |
| sdk | 1.30 s, 60 MB | 0.81 s, 46 MB | 10-13 s on the phone | |
| subsdk0 | 0.60 s, 30 MB | 0.38 s, 25 MB | 5-7 s on the phone | |

Where the memory went: Python's 3.0 M cached `Instruction` objects and the per-piece buffers are gone. The image is
allocated once and the LZ4 segments are decompressed straight into it, the input is memory-mapped, `ORIG_TEXT` (a 121 MB copy)
is replaced by a log of the original words of the text words actually changed, the 30 M-word text is never copied (the
Snowdrop detector read it through a tuple of ints in Python), functions are decoded one at a time and dropped, spin-wait
instructions are decoded on demand per worker (no global cache), and the patch area is written straight to the output.
Where the time went (main, 1 thread, ms): detectors ~1.7 s (function fingerprints of the match rules and Monolith, Unity icall
table), linear scan 0.5 s, per-function analysis 1.2 s, spin-wait search 5.5 s (456 k candidate heads, 85 k pass the cheap
reachability test, 1.2 M decodes), output ~0.3 s. Three changes did most of it: the x18 scan only asks Capstone about words whose
register fields (bits 0, 5, 10, 16) contain 18 (a superset of what can name x18 / w18, verified against Capstone on 6.8 M
words and a unit test; 42 s -> 0.6 s), `spin_quick` before decoding the lock sequence at a head, and no `regs_access` for
spin-cache instructions. Rayon runs the linear scan and the spin-wait search (read-only, results keyed by address, so output
does not depend on the thread count).

## Per-game patches

Python loads every `dm/games/<id>/patches.py` with `importlib`. Rust has a static registry instead (`patches.rs` + generated `tables.rs` + the ported stub functions in
`stubs_games/`). `tools/gen_patch_tables.py <engine>/dm [--coverage coverage.tsv] > src/tables.rs` reads the **28 patch files** of the shipped engine (+ `sdk_patches.py`,
`engine_patches.py`) once at development time and emits everything that is data: `CUTS`, `OBS`, `CAPABILITIES`, the SDK-wide / engine-wide / per-profile `MATCH_CUTS`; the build IDs of
`FRAME_STEP` / `STUBS`; the rules of `MATCH_FRAME_STEP` / `MATCH_STUBS` (name, size, fingerprints, `others`, the imported symbol of an anchored rule, `fps_required`); and a **code digest**
per patch file that has code-valued tables (sha256, 16 hex digits, of the source of every top-level statement the stub tables reach, comments and the data tables left out; the same on
Python 3.9 and 3.14). `coverage.tsv` is the machine-readable list of everything the patch files register (kind, profile, key, digest, game).
* **Grizzy (`0100DFA027504000`) has no `patches.py`** (and no profile folder): its modules get no registered cuts; the SDK-wide / engine-wide `MATCH_CUTS` all miss and are reported in
  `<name>.match.tsv` and the log. Covered by `tests/oracle.rs`.
* **The stub functions are code** and are ported by hand (`FRAME_STEP[build]`, `STUBS[build]`, the `stub` of each rule; Hades II's anchored `find`). Each file of `stubs_games/` has a
  `GamePort` that lists them and records the patch file's code digest the port was verified against. A build whose port is missing or older than the tables' digest stops the rewrite
  with `"<game> (<profile>, <module> build <id>): its <table> patch is code that this version of the app does not include yet (...); update the app"`, never a silent rewrite without it.
* **Durable against engine updates:** `tests/patch_coverage.rs` (always: every registration of `tables.rs` has a port with the current digest; with the engine tree: runs
  `scripts/check-patch-coverage.sh`) and `scripts/check-patch-coverage.sh [<engine>/dm]` (regenerates the tables and the coverage list from the engine, compares them with `tables.rs`
  and with `ibuilder-rewrite --list-ported`, and FAILS listing every build / rule the Rust cannot rewrite and every stale table; prints `SKIP` and exits 0 without an engine tree).
  Redo a port after an update: regenerate the tables, port what the script lists, `tools/stubtest.py --export` against the engine's real Python, put the new digest in the `GamePort`.

## Update (R5, 2026-11-21): the synthetic manifest, jump-table parity, review r3/r4 items, performance

### The synthetic manifest: one format, one writer (r4 §3.1 / §4.3)

*(R6: the format below was simplified once the jump solver was ported: no older engine, no statuses, an `error` row for a case the Python stops on; see "Update (R6)".)*

`cargo test -p ibuilder-rewrite` was red: `tests/synthetic.rs` reads the 5-column manifest with the `#! shipped-engine` / `#! older-engine` / `#! status` headers that
`tools/synth_manifest.py` writes, but the file on disk was still the 4-column one, and `tools/export_fixtures.py` still wrote that old format (two generators, two formats).
Now **`tools/synth_manifest.py` is the only writer** (`write(cases, fixtures dir)`; run alone it rewrites the manifest of the fixtures in the folder, reading the case list from
either format) and `tools/export_fixtures.py` builds the `.nso` fixtures (its template cases are kept when the SHIPPED engine's Python rewrites them) and calls `write()`.
Format, tab-separated, read by `tests/synthetic.rs`:
```
#! shipped-engine  <first line of out-stage/out-engine/stamp.txt: source revision>  <sha256 of that stamp.txt>
#! older-engine    <revision of the engine the Rust recognisers were ported from>
#! status          <case>  python-stops | shipped-differs  <what the shipped Python does>      (only the cases that are not parity cases)
<case>  <module name>  <file kind (stdout, patched.bin, fixups.tsv ...)>  <sha256>  <oracle: shipped | older | shipped-differs>
```
A parity case has only `shipped` rows and the Rust must give them; a `python-stops` case has only `older` rows; a `shipped-differs` case has the `older` rows the Rust must give and the

### Jump tables: the shipped engine is right, the Rust differs (r3 §3.2)

Regenerated evidence (`tools/difftest.py jt 0 40`, the Rust CLI against each engine's real `patch_nso.py`): **older engine 40 identical of 40; shipped engine 18 identical, 19 where
the Python stops, 3 where it writes other sites** (the "22"). The 22 are exactly the hand-built variants `off`, `adr_off`, `off_far`, `off_fn2` and `half`; the 18 identical ones are
`tail`, `off_mov`, `off_masked`, `byte`. The cause, read off the fixtures' code (`jt_off`: `cmp w0, #2; b.hi; adrp x17; add x17; ldrsw x18, [x17, x0, lsl #2]; add x18, x18, x17;
br x18`; `jt_half`: `... ldrh w1, [x17, x0, lsl #1]; add x18, x18, x1, lsl #2`): **the guard compares the 32-bit `w0` and the table is indexed with the 64-bit `x0`**, whose upper 32
bits that compare does not bound. The shipped engine's `jump_solver.py` (dataflow over the function) says so: "the index reaches 0xffffffffffffffff", an `AssertionError` that stops
the whole module, and for a halfword table it gives all 65,536 pads (`half_pads` has no proven size). The older recognisers, and the Rust's `jumps.rs` ported from them, take the
compare as the bound. Where the index is zero-extended or masked (`off_mov`: `mov w1, w0`; `off_masked`: `and x1, x0, #7`) both engines agree with the Rust. **So the shipped
Python is the correct one and the Rust is not conforming on this form**; a real module with such a table would be refused by the shipped engine and rewritten by the Rust. Real
data agrees (Grizzy and Ocarina of Time: every file identical, Ocarina's main has 94 `br x18` sites). The fix is to port `jump_solver.py` (704 lines) and its integration in
`patch_nso.py` (`branch_entries`, the landing pads of `nso_code.landing_pads`, `half_pads`, the second reading over the control flow): **not done in R5; done in R6** (below).

### Performance (R5): what changed, and the byte-identity proof

## Update (R6, 2026-11-22): the shipped jump solver ported (r3 §3.2)

The rewriter now proves offset jump tables the way the SHIPPED engine does (engine `75c73361`, stamp sha256 `be6c194a...`: `out-stage/out-engine/engine/dm/tools/jump_solver.py`,
704 lines, and its integration in that `patch_nso.py`). The 5 synthetic cases that differed in R5 now give the shipped Python's answer: `jt_off`, `jt_adr_off`, `jt_off_far`,
`jt_off_fn2` stop the module with `jump table N: the index reaches 0xffffffffffffffff` (the guard `cmp w0, #n` bounds the 32-bit `w0`, the load indexes with the 64-bit `x0`),
`jt_half` writes the shipped files (65,536 pads: no proven size). Grizzy and Ocarina of Time stay byte-identical to their oracles.

### What was ported

* `src/jump_solver.rs`: `jump_solver.py` line for line (values, roots and chains, the 4096-bit low-bit sets, `_eval` / `_refine` / `_pred` / `_cond`, `Function.step` / `data` /
  `join` / `run` / `starts` / `solve` / `read` / `table`, the two readings of `solve`). What makes the Python's answer what it is, beyond its arithmetic, is kept:
  * Python integers: every value is an `i128`;
  * the ORDER of the fixpoint: the widening after `WIDEN` visits and the order of the results depend on the order the work list visits states, and the Python seeds it by
    iterating a `set` of ints, whose order is its hash table's. `src/pyset.rs` keeps CPython 3.14.1's table (`Objects/setobject.c`: linear probes, perturbation, dummies, resizes,
    `set_merge`, `set_difference`), so the seeds (`{0} | calls | {...}`, `seeds |= starts() - seeds`), the `br x18` set and the sets of direct entries patch_nso.py passes iterate
    as they do there; states, constraint maps and results follow dict insertion order;
  * the Python's exceptions: `Unsupported` (`no fixpoint`, `<mnemonic> at 0x...`) fails every `br` of the function, as `solve` does; a `TypeError` of `State.key` (its
    `sorted(cons.items())` cannot order a root `('x', root, i, 64)` against a root `('x', k, i', i, 64)`) stops the module in the Python and here (same message), found by
    replaying CPython's `list.sort` for fewer than 64 items (`count_run` + binary insertion) on the same keys in the same order (`py_sort_check`), only when both root shapes
    are present.
* `src/scan.rs` (`Solver`), as the shipped `patch_nso.py`: per `br x18`, the 16-instruction form (`adr x18` + `add x18, x18, xI, lsl #2` + byte load: 256 pads; halfword load:
  `half_pads` from the solver's table, else 65,536), else `jump_bytes_far` (halfword: `half_pads`), else `table_at` (the solver's targets), else a tail call, else the module stops
  with `jump table <at>: <why>`. `branch_entries` (direct branches into each range from elsewhere, in the Python's set order), `nso_code.landing_pads` (`fde.rs`), and the
  re-proof of the functions that tables elsewhere enter (`jump table <at>: an entry from another function is not proved`). Removed with the older engine: `jump_offsets`,
  `jump_adr_offsets`, `jump_masked_pred`, `jump_guarded_tail` and its "past a guard" checks, `jump_guarded_cfg` and its re-proof, `half_count`, `null_base`, `writes_reg_any`.
  Also from the shipped engine: `tail_call_padded` accepts `nop` padding; pointer encoding 0x01 (uleb128) in `fde.rs`.
* `ibuilder-a64/src/cs.rs`: what the solver reads of Capstone beyond R5's fields: `Op::shift_value`, `Op::shift_type()`, `Op::ext()` (packed in two bytes: `Op` stays 24
  bytes) and `Ins::update_flags`.
* Message parity found on the way (`tools/difftest.py` Grizzy-chunk seed 283): `branch leaves window with live reservation -bfc` (a target before the module: Python's `{x:x}` of a
  negative number); the Rust printed the two's complement (`windows.rs`).

Speed and memory: the solves are pure functions of the image and the ranges, so with several workers the ranges the loop is likely to solve (`may_solve`: a `br x18` that is not
the 16-instruction byte form, judged on the words) are solved ahead in parallel and taken when the loop asks (a range missed is solved when asked, one taken wrongly is never
read: the answers and the error order are the lazy ones); the direct entries are built only for those ranges (one scan; a range's set does not depend on the others'); landing
pads are a flat sorted vector; a call's state is kept only when the function has landing pads; the solver is dropped before emission.

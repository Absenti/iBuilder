## 2. Mario Kart 8 Deluxe from a merged XCI: stage 2 `KeyError: 2`

* The import log says `leaving out 5 NCAs ... (another title in the package: an update on the cartridge, or a merged NSP)` and `display version 1.0.0`: the package carries the 4.0.0 update beside the base game, and the app read
  **the base game only** (it passes `-` as the update argument unless a separate update file was imported).
* That base build's `main` (8,365,644 bytes, build id `b5c39b5b7c62a88ec25fa897858c874e`) is a **32-bit AArch32 program**: `main.npdm` has Is64BitInstruction = 0 (address space type 2), 99.9 % of its text words decode as
  ARM instructions (31.8 % as A64), the build id matches neither registered build (4.0.0 `2c336a9b…`, 4.0.1 `158c0c73…`). The rewriter (Rust and the engine's Python alike) reads the unwind table first and trips on
  garbage: the first pointer encoding byte is 0x62, so the format 2 is not in its `{3, 0xB, 4}` table: `KeyError: 2`. Reproduced on the Mac with the module copied from the phone: Rust and Python fail identically.
* Apple's A-series cores have no AArch32: a 32-bit Switch program cannot run natively on an iPhone, whatever the toolchain does. The registered updates 4.0.0 / 4.0.1 are the builds the engine handles.

What was changed (so the next such case does not cost a build and a puzzling message):

1. `ibuilder-pipeline/src/preflight.rs`: before stage 2 reads any module, `main.npdm` is checked (32-bit program: **refused at once**, with the build id and the "an update may have been left out" hint) and `main`'s build id is
   compared with the profile's `build` rows (unknown build: a warning in the log). A rewriter failure whose text is a known low-level signature (`KeyError: n`, a missing MOD0, not an NSO) gets a sentence saying what it
   usually means. Tested on the real files from the phone (`PREFLIGHT_MK8D_EXEFS=<ExeFS dir> cargo test -p ibuilder-pipeline preflight`) and on synthetic ones.
2. `app/patches/nx_extract_merged_update.py` (applied by `scripts/build-app.sh` to its copy of the engine's `nx_extract/Program.cs`): when no update file is given and the package itself holds a Patch content meta of the base
   game's title (id | 0x800), those NCAs are the update; the extractor already supported "a merged package given as both the base game and the update", the app just never did it for one file. **Not tested on real data**: no
   merged package is on this Mac (the merged XCI is on the phone); the patch compiles into the app and changes nothing for a package without an update meta or when an update file is given.

## 2026-11-19 (evening): first USB tests on an iPhone 15 Pro (iOS 27.0.1), Mario Kart 8 Deluxe v4.0.0 merged XCI

Phone on the cable, app signed by Xcode (`scripts/usb-install.sh`), hidden diagnostics on (`docs/DIAGNOSTICS.md`).

* **Build on the phone:** 11 min (rewrite 1.8 s, 29,650 shaders translated in 634 s with a peak of 901 MiB, the heat gate paused it for a while); the update carried by the merged XCI was merged; a library that exists is not rebuilt (a second "Set up" took 49 s: the framework only).
* **Cover missing:** a dump whose file name carries no title id (a merged `.xci`) had no cover and nothing keyed on the id: fixed by reading the id from the package (patch 0051).
* **Black screen / 0 fps at the first launch:** the host prepares the seed list's pipelines before the first frame: 50 s for 1,359 lines on a cold Metal cache (the engine's progress screen is not visible on the phone). The pipeline binary archive then makes the next launches start in 3 s ("present #1 at t=3.269 s", 1,116 render pipelines prewarmed with the merged seed list).
* **Black 3D scene in a race, UI visible:** the host draws nothing for a pipeline that is not built yet ("built in the background, its draws skipped meanwhile", DM_PSO_NOWAIT): a race needs pipelines the title and menus never used. The player reported "after several launches it is better, 60 fps": the host records what the game built (`games/<id>/pso_user.tsv`) and prewarms it next time. `app/game-tables/0100152000022000/pso_manifest.tsv` now ships the engine's 1,516 rows + the 3,093 learned in one session (`scripts/build-app.sh` replaces the engine's table with it).
  Engine patch 0403 was suspected and ruled out by a build without it (same behaviour).
* **Frame rate:** 58 fps average over 60 s of menu once warm (2 % long frames); 15 fps in a race on the first visit, with the phone at thermal Serious and, for a while, in Low Power Mode (the diagnostics log both). The old host (no engine patches) shows the 3D scene but keeps a 4.4-4.7 GB footprint (the new one 2.0-2.7 GB).
* **Audio crackle (root cause found with the diagnostics):** "audio #0 device callbacks 4000: 1024–1024 frames each, 4.0 blocks queued on average at callback; in these 2000, 2002 underruns, 2671.7 ms zero-padded". The AVAudioSession of this app was never configured (the engine does it in `front_ios.m`, which the loadable host does not carry), so RemoteIO asked for 1024 frames per callback while the guest keeps 4 x 240 = 960 queued: every callback 64 frames (1.33 ms) short, 47 gaps a second. `GameAppAudio.cs` (patch 0053) sets Playback / 48 kHz / 5 ms as the engine does: **240-frame callbacks, 0 underruns in the first 2,000 callbacks, 14 (35 ms) in the next 2,000.**
* **Background build task refused** ("the system refused the task registration"): the task id is the runtime bundle id + ".build.<n>" and a cable install is `dev.nxpocket.gameapp.usb` (a SideStore install `dev.nxpocket.gameapp.<TEAM>`): patch 0052 adds `dev.nxpocket.gameapp.*` to the permitted identifiers; the refusal was still logged by the build that carried it (not yet understood).
* **Confirmed by the player:** with the seed list merged and the audio fixed, the FIRST race is still black in 3D (112 libraries compiled from source in 15.6 s, "its draws skipped meanwhile"); at the **second launch the screen is no longer black** (the system's Metal compile cache holds those libraries). So the cause is the host's skip-while-compiling policy on a cold cache, not a missing shader or a host patch.
  Now `DM_PSO_NOWAIT=0` is the game env default (`profile.rs set_game_env`, `pso_nowait=1` or an env.txt value keeps the host's own): the draw waits for its pipeline, the scene is visible and hitches for a few seconds instead of staying black. The lasting fix is the warm-up ("Prepare the shaders", `GameAppWarm.cs`: compiles the pack's libraries into the system cache once); it was not run in these tests (about 25 minutes estimated for 29,650 libraries, not measured).
* **Slowdowns the player reported after the wait policy (one session, 31 samples, thermal Serious all along):** 451 dropped frames logged, 411 of them in the first ~30 s (frames 0-1800), then about 2 % of frames. Dominant cause of the dropped frames: waiting on the GPU (`sync_ms` median 21.9 ms, GPU 19-21 ms per frame at Serious; 381 of 451), CPU recording for 70. One frame took **13,682 ms** (frame 1383, 1,306 draws): the start of the race with the draw waiting while the 112 libraries compiled in one go (the price of `DM_PSO_NOWAIT=0`; skipping the draws gave a black scene instead). Merged the 3,568 pipelines learned in two sessions into `app/game-tables/0100152000022000/pso_manifest.tsv` so they are prewarmed BEFORE the first frame (a longer first prepare, no freeze at the start of a race); the lasting fix remains the warm-up.

* **Is the host's pipeline binary archive portable between apps? Mac probe, 23:50 (the iPhone test is NOT done: the phone holds no real game, no prod.keys, no build, no archive, only iBuilder and two empty placeholders).** What the host does (iOSBuilder `paches/0009`, read only): each pipeline built through the device path is also added, off the submit thread, to one `MTLBinaryArchive` per game, `<game folder>/pipelines-<chain>-<gpu>.mtlarchive` (the folder of `DM_SAVE`, or `DM_PSO_BINARY_DIR`), capped at `DM_PSO_ARCHIVE_MB` (256 by default: at the cap nothing more is added), written at most every 60 s and when the app goes to the background; a pipeline is looked up there first (`binaryArchives` + `FailOnBinaryArchiveMiss`). Beside it a `.hdr` file holds the host build (`__DATE__ __TIME__`), the shader chain, the OS version string and the GPU architecture name: any difference and the file is dropped at start (so an export carries a usable archive only from the same host build, OS build and GPU). The archive holds the GPU binaries of the pipelines, NOT the libraries: the functions a descriptor needs still come from the source compile (or a .metallib), so the front-end cost stays. Probe (`archtest.swift`, a Mac command-line tool in the scratch folder, one compute and one render pipeline of a 300-statement shader, M1 Pro): written by a process signed as `dev.probe.a`, the archive (248,624 bytes for the two pipelines) was loaded by a process signed `dev.probe.b` with `FailOnBinaryArchiveMiss`: HIT for both, 0.2 ms each, against 163 / 130 ms to build them into the archive and 172 / 123 ms for a third identity with no archive. So at the API level an archive carries no app identity. The library from source took 307 ms cold and 7-10 ms in the other processes: the macOS source cache is shared by the user, which is NOT the case in an iOS container, so the library timings say nothing about the phone. In this synthetic case the pipelines are about half of the cold compile (293 of about 600 ms); for the game the split is not measured. NOT shown: that an iPhone behaves the same (other GPU and driver, sandbox, a FlareStore signature), the game's own numbers (about 4,927 pipelines, 120 KB per pipeline here would be about 600 MB: the 256 MB cap would keep only part), and the gain on the 268 s.
